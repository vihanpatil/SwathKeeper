State as of 2026-08-04 (Week 2 hand-off: mission-through-farm-world wiring + geofence consumer).

## What exists in `src/` today
- `src/fieldguard_planning/` — **not yet a real colcon/ament package** (no `package.xml`/`setup.py`).
  Pure stdlib-only Python, imported via `sys.path.insert(0, ".../src")`. Two modules:
  - `geofence.py` — the ADR-001 static-obstacle geofence consumer. `GeofenceMap.from_file(path)` ->
    `is_point_excluded(x,y)`, `excluding_obstacle(x,y)`, `point_clearance(x,y)` (signed, negative =
    inside), `segment_clearance(p1,p2)` / `check_path(points)` for mission-leg checks (exact
    point-to-segment math, not sampled).
  - `mission_waypoints.py` — QGC WPL 110 parser (`parse_qgc_wpl`) + lat/lon<->local ENU meters
    conversion (`latlon_to_enu`, exact inverse of `scripts/gen_boustrophedon.py`'s `to_ll`) +
    `mission_xy_path()` which flattens a parsed mission into the ordered XY polyline actually
    flown (handles the NAV_TAKEOFF/RTL placeholder-(0,0)-lat/lon trap — those items climb/return
    **in place** over the current position, not literally at (0,0) lat/lon).
- No `rclpy` nodes exist yet anywhere in the repo. No `fieldguard_msgs`, no `fieldguard_control`,
  no `fieldguard_bringup`. When Week 3-4 avoidance-loop nodes get built, `fieldguard_planning`
  should be promoted to a proper ament package at that point (not before — no reason to pay colcon
  build cost for pure logic that's fully testable via `sys.path`).

## Key control parameters / constants worth remembering
- Field: `config/field_polygon.json` — 75m(E) x 60m(N) rectangle, home = (-35.363262, 149.165237),
  mission altitude 15m. `config/missions/boustrophedon.waypoints` is generated by
  `scripts/gen_boustrophedon.py --width 80 --height 60 --spacing 15 --alt 15` and **regenerates
  byte-for-byte identical** to the checked-in file from current `config/` — confirmed via diff,
  Week 2. 6 lanes at x=0,15,30,45,60,75.
- Trees: `config/static_obstacles.json` — 18 trees, 3 rows at x=15,40,65 (y=5..55, spacing 10m).
  `obstacle_radius_m=2.0` is the field to geofence on (not `canopy_radius_m=1.3`, which is only the
  Gazebo collision geometry). Tree height 3.5m vs mission altitude 15m = 11.5m vertical clearance.
- **XY geometry finding (Week 2, via `scripts/check_mission_geofence.py`):** tree row 0 (x=15)
  sits *exactly on* mission lane x=15 (not offset like rows 1/2, which sit 5-10m off their nearest
  lanes) — the lane's return leg has **-2.0m XY clearance** (flies directly along the row
  centerline). Safe only because of the 11.5m vertical margin. Every other leg clears by >=3.0m
  XY. This is the number to reach for if Week 3-4 avoidance work needs a scenario that forces a
  real XY dodge (lower altitude and/or raise tree height) — row 0 is already primed for that; rows
  1/2 are not.

## ArduPilot/MAVLink gotchas (inherited from robotics-sim-engineer's WEEK1_BRINGUP.md — not
rediscovered by me, just tracking since they're load-bearing for anything I build on top)
- `GZ_SIM_RESOURCE_PATH` must include `ardupilot_gazebo`'s `share` dir or the whole world fails to
  load (`Unable to find uri[package://ardupilot_gazebo/...]`).
- First SITL boot after a fresh build shows `Frame: UNSUPPORTED` — `FRAME_CLASS`/`FRAME_TYPE` params
  only apply after a `reboot`, not just `param set`.
- `DISARM_DELAY 0` needed or the vehicle auto-disarms ~10s after arming before a mission starts.
- `AUTO_OPTIONS 3` needed to allow arming + auto-takeoff directly into AUTO mode.
- AP_DDS (`/ap/*` ROS 2 topics) is NOT enabled by default on gazebo-iris params — separate from
  flying a mission (which only needs MAVLink), needed later when ROS 2 control nodes consume
  telemetry.

## Launch/run helpers I added (Week 2)
- `scripts/run_farm_mission.sh` — Shell A wrapper (starts `farmguard_field.sdf` with correct env),
  prints the Shell B recipe. Shell B stays manual/interactive on purpose (EKF-ready wait, one-time
  frame reboot) — see script header for why blind automation was rejected.
- `scripts/check_mission_geofence.py` — CLI sanity check: mission XY path vs. geofence, per-leg
  clearance report, exit code 1 on any violation (there's currently exactly one, the row-0/lane-15
  overlap above, which is expected/documented not a bug).

## Environment-honesty pattern to keep following
Per this project's standing constraint (this session has no Docker/Gazebo/ROS 2), only pure-logic
modules (geofence, mission parsing, coverage-debt data structures) can be authored + tested here.
Anything requiring `gz sim` / SITL / rclpy needs the human-operated Docker container
(`scripts/sim_docker_run.sh`). State this split explicitly in every hand-off rather than implying
something was "tested" when it was only statically validated.
